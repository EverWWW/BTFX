# DAHENG 正式录制链路优化设计

## 目标

- 点击开始录制后进入 5 秒倒计时，倒计时结束即开始写入视频，不再等待相机和编码器初始化。
- 倒计时和正式录制期间均显示低帧率实时画面，保存视频仍使用用户选择的 30/60/90 fps。
- 保持当前双相机统一起始时间的同步策略。
- 降低大尺寸逐帧分配、无界队列积压造成的频繁 GC 和内存上涨。

## 当前根因

1. ViewModel 在倒计时之前停止实时预览并释放 DAHENG SDK；倒计时结束后才调用录制服务。
2. 录制服务调用后才重新初始化 SDK、打开两台相机、加载 UserSet0、配置参数并启动两个 FFmpeg 进程。
3. XAML 中实时预览图像只在 Preview 状态可见，Recording 状态仅显示文字层。
4. 2048x1536 BGR24 单帧约 9 MB，当前每个回调都创建新数组；双相机高帧率会产生极高的托管堆分配率。
5. 当前录制使用 `Channel<byte[]>` 无界队列，编码速度低于采集速度时会持续积压大数组。

## 推荐架构

### 录制时序

1. 用户点击开始录制，ViewModel 计算统一的计划开始时间 `T0 = 当前时间 + 5 秒`。
2. 立即停止旧预览并释放旧设备占用，然后调用 DAHENG 录制服务。
3. 服务在倒计时内完成相机、采集流、转换器、编码器和输出文件准备。
4. 两台相机准备完成后立即开始连续采集，采集帧只用于低帧率 UI 预览。
5. 到达 T0 后，两台相机按同一个时间基准开始写入录制队列。
6. 到达目标时长或目标帧数后停止入队，等待编码器完成写入并关闭输出文件。

如果设备准备超过 5 秒，不伪装成已经开始录制；界面显示“正在准备录制”，所有设备就绪后使用一个短同步缓冲再开始，并记录实际延迟。

### 录制期预览

- DAHENG 在倒计时和正式录制阶段保持实时画面可见。
- UI 预览限制为约 10 fps，使用可复用的 `WriteableBitmap`。
- 预览帧允许跳过；保存视频帧不因 UI 忙碌而丢弃。
- 录制状态、倒计时和已录制时间以半透明叠层显示在画面上。
- 转码/封装阶段停止实时预览，改为显示处理状态。

### 内存与队列

- 录制帧缓冲使用 `ArrayPool<byte>` 租用和归还，避免每帧创建约 9 MB 数组。
- 队列元素包含缓冲区、有效长度和重复写入次数；补帧不复制整帧数组。
- 写入线程完成该队列元素后立即归还缓冲区。
- 队列改为容量受控，防止编码器短暂变慢时无限增长。
- 队列满时记录诊断数据；不静默丢帧。必要时用最近有效帧维持目标时间轴，并在日志中统计。
- 预览缓存与录制缓存分离，避免 UI 异步读取已经归还或重用的录制缓冲区。

## 状态与日志

新增或规范以下状态节点：

- `PREPARING`：打开设备、配置相机、启动编码器。
- `COUNTDOWN`：设备已采集预览，等待统一开始时间。
- `RECORDING`：正式写入视频。
- `FINALIZING`：停止采集并等待编码器完成。
- `DONE` / `FAILED` / `CANCELED`。

每台相机记录：设备准备耗时、首帧时间、正式录制首帧时间、采集帧数、入队帧数、写入帧数、补帧数、队列峰值和最终文件路径。

## 兼容边界

- YUNXI 保留现有录制和转码流程，不改变其录制期间关闭预览的行为。
- DAHENG 保留当前 30/60/90 fps、默认 2048x1536、SN 配置和图像方向设置。
- 不改变录制结果回填新建测量页面的接口。
- 不改变现有双相机统一计划起点的同步策略。

## 验证标准

- 5 秒倒计时期间可看到两路实时预览。
- 正常设备环境下，倒计时归零后 300 ms 内进入正式录制状态。
- 录制期间两路画面保持可见，预览约 10 fps，录制文件仍为选择的目标帧率。
- 连续执行三轮双相机 10 秒录制，托管内存不随轮次持续增长。
- 队列有明确上限，日志中的写入帧数与目标帧数一致；发生补帧或队列压力时有可定位日志。
- 输出视频可由 ffprobe 正确读取，时长、帧率和帧数符合配置。
